# 项目审查与优化计划

- 审查日期：2026-10-20（北京时间）
- 审查对象：`dsh-purge`，包版本 `1.1.74`
- 审查基线：提交 `abccb97`
- 文档性质：问题记录、优化建议与后续修复验收依据；不代表已经实施修复
- 审查方式：源码阅读、静态检查、隔离文件测试、临时数据库验证和内存构建比对

## 1. 结论摘要

项目已经具备备份、原子替换、目录链接保护、生命周期清理及部分回归测试。当前应优先增强三件事：

1. **更新可靠性**：更新资源齐全，失败不会损坏现用安装，状态不误报成功。
2. **数据正确性**：局部更新不覆盖缺省字段，重复导入不放大当前数据与统计。
3. **发布可重复性**：源码能生成当前分发产物，测试和运行时要求进入发布门禁。

本轮发现 8 项主要问题，另列 1 项归档兼容性问题与 4 项工程改进建议。应先修正确性和恢复能力，再依据基准进行性能优化，不建议立刻大规模重写。

### 1.1 优先级定义

| 优先级 | 含义 |
| --- | --- |
| P1 | 优先修复：可能破坏安装、越过文件目录边界、改变已确认数据，或使必要资源未更新 |
| P2 | 随后修复：导致统计失真、构建回退、并发失败或平台行为异常 |
| P3 | 计划改进：提升可维护性、可重复性和排障效率 |

这些优先级是项目排期建议，不是经过完整威胁建模或正式评分得出的漏洞等级。

| 编号 | 优先级 | 问题 | 证据类型 |
| --- | --- | --- | --- |

## 3. 主要问题与验收标准

### R01：ZIP 覆盖更新缺少事务与失败恢复

**优先级：P1。证据：静态控制流确认，未执行真实更新。**

位置：[update.js:878–913](<../lib/update.js#L878-L913>)。

#### 现象与触发条件

`overlayFromZip` 逐目标、逐项目修改现用安装树。对于 `lib`、`docs`、`bin`，先递归删除目标，再执行复制。

删除成功后，如果复制遇到磁盘满、权限错误、文件占用或进程中断：

- 旧目录已经删除，新目录仅复制一部分。
- 后端代码、前端产物和包版本可能来自不同版本。
- 多个安装目标可能只有部分更新成功。

删除失败时的异常处理不能保护删除成功后的复制失败；末尾清理仅移除下载临时目录，没有恢复现用树。

#### 建议

1. 在目标同卷的暂存目录准备完整新版本。
2. 提交前验证包身份、版本及必需资源。
3. 切换时保留旧目录，并记录可恢复的事务状态。
4. 多目标更新明确采用整体回滚还是逐目标提交，界面如实呈现部分成功。
5. 文件切换、必要验证完成后，最后提交版本与历史状态。

#### 验收标准

- 在暂存复制、提交切换和多个目标更新之间注入失败，旧安装仍可读取并恢复。
- 更新中断后，下次启动能够识别未完成事务，恢复或明确要求人工处理。
- 失败不清除唯一可用备份，不误标为更新完成。
- 测试全程使用临时安装树，不接触实际宿主。

### R02：更新复制清单遗漏发布目录

**优先级：P1。证据：清单比对确认。**

位置：[更新复制清单](<../lib/update.js#L20-L31>)、[包发布清单](<../package.json#L21-L34>)、[演练台资源路径](<../lib/redteam/index.js#L25-L34>)。

#### 现象与影响

发布清单包含 `presets`、`skills`、`scripts`，但 ZIP 覆盖更新的 `COPY_NAMES` 不包含这三个目录。

因此通过该路径更新时，代码与包版本可先更新，而预设、技能、环境脚本仍保留旧版。该结论限定于 ZIP 覆盖更新路径，不推断所有安装方式都有相同问题。

#### 建议

- 发布和更新使用同一份经过校验的资源清单。
- 明确区分随包资源与用户可编辑数据，禁止更新清单扩大后误覆盖用户数据。
- 发布时检查必需资源存在，更新时检查目标资源版本一致。

#### 验收标准

- 从旧版本临时安装树更新后，三个目录中的随包资源均与目标版本一致。
- 自定义配置与用户数据保留。
- 自动检查能发现发布清单与更新清单不一致。

### R03：文件路径边界校验不完整

**优先级：P1。两个独立入口分别验收。**

#### R03-A：ASAR 普通文件可写出解包目录

位置：[目录遍历](<../lib/extract-asar.js#L270-L277>)、[解包写入](<../lib/extract-asar.js#L432-L469>)。

`walk` 直接使用归档头文件名构造相对路径。普通文件输出路径经拼接后直接创建父目录并写入；现有目录归属校验只覆盖链接目标，没有覆盖普通文件。

**复现结果：**在专用临时根内制作异常归档，调用纯文件解包函数，成功在指定解包子目录之外写入测试文件，但未离开专用临时根。

**影响前提：**归档条目异常、归档被替换或来源不可信。不据此断言官方归档已经遭到篡改。

**建议：**在落盘前预检全部条目，拒绝父级路径、绝对路径、盘符及平台异常名称；输出路径规范化后必须处于目标根内，写入前检查父路径链接。

**验收标准：**非法条目在任何文件写入前被拒绝；正常文件可解包；绝对路径、父级路径、链接越界和 Windows 路径变体均有隔离回归测试。

#### R03-B：技能读取兜底可读取技能根外的 Markdown

位置：[技能文件读取](<../lib/redteam/ui.js#L875-L894>)、[异常兜底入口](<../lib/redteam/ui.js#L1133-L1144>)。

名称只检查非空，随后直接拼接并读取，没有要求名称属于已枚举的技能清单，也没有检查真实路径归属。

**证据：**静态路径确认，未访问运行中接口或真实敏感文件。触发需要进入文件兜底分支，并存在对应的目标 Markdown 文件。

**建议：**只接受清单成员；对真实路径限定根目录，防止名称分隔符和符号链接造成越界。

**验收标准：**正常技能可读取；目录外名称和指向目录外的链接被拒绝；拒绝结果不返回目录外正文。

### R04：已有漏洞的增量更新改变缺省字段

**优先级：P1。证据：临时数据库复现。**

位置：[addVuln](<../lib/redteam/store-core.js#L2142-L2169>)、[报告过滤](<../lib/redteam/store-core.js#L5022-L5026>)。

#### 已验证现象

1. 创建严重级为 `high`、状态为 `confirmed` 的本地测试记录。
2. 通过相同记录标识再次提交，仅补充 `evidence`，不提供 `severity`。
3. 记录严重级从 `high` 变为 `info`，证据被更新，状态保持 `confirmed`。
4. 在已有记录更新分支传入非法状态字符串，该字符串被原样写入。

原因是创建默认值与更新值共用：缺省严重级先变为 `info`，更新分支无条件覆盖；状态虽然计算过规范值，更新绑定时却使用原始输入。

默认报告只保留中危及以上且已确认或已利用的记录，因此意外降级会使记录退出默认交付报告。

#### 建议

- 创建与局部更新分开处理。
- 更新只写入显式提供且校验通过的字段。
- 区分字段缺省、显式清空与非法值。
- 统一不同更新入口的枚举校验语义。

#### 验收标准

- 仅补证据不改变严重级、状态及其他未提供字段。
- 显式修改合法严重级能成功。
- 非法状态被明确拒绝或按统一规则处理，不原样入库。
- 报告纳入规则在仅补证据前后保持一致。

### R05：桌面换包非终止错误被误判成功

**优先级：P2。证据：独立 PowerShell 文件操作语义复现，未运行实际重启脚本。**

位置：[脚本错误策略](<../lib/desktop.js#L864-L870>)、[移动与成功分支](<../lib/desktop.js#L913-L932>)。

脚本采用 `Continue` 错误策略，关键 `Move-Item` 未使用 `-ErrorAction Stop`。文件被占用等非终止错误不会进入 `catch`，后续仍设置成功标记并退出重试。

临时文件占用验证结果：

```text
moved=True
sourceStillExists=True
backupExists=False
```

#### 建议与验收

- 关键移动使用终止错误语义。
- 宣布成功前验证源、目标状态，不只依赖变量赋值。
- 失败保留待处理标记和可读错误，不走成功启动分支。
- 在临时文件被占用、目标存在、权限不足等场景验证，不启动或终止真实宿主。

### R06：服务重复导入放大列表及统计

**优先级：P2。证据：临时数据库复现及查询链确认。**

位置：[导入服务](<../lib/redteam/store-core.js#L5226-L5249>)、[资产关联和端口统计](<../lib/redteam/store-core.js#L1240-L1257>)。

相同资产和端口重复导入时，端口更新原记录，但服务无条件新增。相同测试数据导入两次得到：

```text
端口记录数：1
服务记录数：2
```

当前查询直接关联全部服务记录，随后按结果行统计开放端口，导致同一端口重复显示、端口数失真，并随重复采集增加存储和处理成本。未做大规模性能压测，不给出未经测量的性能增幅。

#### 建议

- 明确服务数据是当前快照还是历史记录。
- 当前快照使用合适的唯一键与更新写入。
- 若保留历史，当前视图只选择当前记录，端口计数按端口主键计算。
- 给现有重复数据提供迁移或去重策略。

#### 验收标准

- 相同数据重复导入不改变当前端口数。
- 服务确实变化时能更新当前值，或保留可区分的历史。
- 数据迁移不会丢失非重复的有效记录。

### R07：前端源码与分发产物不一致

**优先级：P2。证据：内存构建比对确认，排除了换行符差异。**

位置：[前端源码请求处理](<../lib/redteam/client.js#L567-L571>)、[分发产物请求处理](<../client.js#L4037-L4054>)、[构建脚本](<../scripts/build-client.mjs>)。

当前分发产物对 HTTP 失败及非 JSON 响应做了处理，源码只有 `res.json()`。按当前脚本重新构建，会丢失这部分分发产物已有的错误处理。

#### 建议

- 明确生成片段的唯一源码，修复只进入源码再构建。
- 为生成产物标注来源，避免人工补丁只落产物。
- 发布前重新构建，并检查生成结果与提交内容一致。
- 长期减少基于文本标记和花括号计数的构建转换，迁移时先加构建回归测试。

#### 验收标准

- 在干净检出上构建后不产生非预期差异。
- 连续两次构建输出一致。
- HTTP 错误、空响应及非 JSON 响应有测试，错误信息不退化为无法解释的解析异常。

### R08：原子写临时文件名存在并发碰撞

**优先级：P2。证据：隔离并发复现。**

位置：[原子写与复制函数](<../lib/core.js#L64-L86>)。

临时文件名由目标路径、进程号和毫秒时间戳组成。同进程、同目标、同毫秒调用可共用临时文件，造成一个调用移动文件后其他调用找不到它，或内容相互干扰。

固定时间戳进行三批并发验证，36 次写入中 31 次返回 `ENOENT`。固定时间戳用于稳定构造碰撞，不代表真实负载一定达到相同比例。

#### 建议

- 使用随机唯一临时文件名，以独占创建方式防碰撞。
- 对同一目标的业务更新明确串行化或冲突语义。
- 将“文件替换原子性”和“读改写并发一致性”作为两项分别验证。

#### 验收标准

- 同毫秒并发写入不共享临时路径，不因碰撞产生 `ENOENT`。
- 最终文件是某个完整合法版本，不出现混合内容。
- 失败清理不删除其他调用的临时文件。

## 4. 额外兼容性问题

### A01：Node ZIP 解包兜底把目录条目当成普通文件

**优先级：P2。证据：隔离文件复现。**

位置：[zip-extract.js:19–25](<../lib/zip-extract.js#L19-L25>)、[zip-extract.js:76–98](<../lib/zip-extract.js#L76-L98>)。

目录名末尾的斜杠被移除后，解包器对所有条目执行文件写入，没有区分显式目录条目。包含目录及其子文件的正常 ZIP 样本在 Node 兜底路径中失败：目录先被写成普通文件，后续子文件解包报 `EEXIST`。

该问题针对 Node 解包兜底，不代表外部解压工具都会失败。

**建议与验收：**保留目录条目信息，目录只创建不写文件；外部工具失败后不要让残留污染下一解包尝试。覆盖显式目录、空目录、仅文件条目、截断归档和路径冲突测试。

## 5. 工程增强计划

### E01：把测试和构建一致性接入发布门禁

位置：[发布流程](<../.github/workflows/release.yml#L27-L32>)、[包脚本](<../package.json#L36-L39>)。

现有发布步骤仅检查少量入口语法和导入，未执行仓库回归测试，也没有验证前端生成结果。

建议增加：

1. 独立的持续集成验证，不只在发布步骤执行。
2. 统一测试、源码语法检查和构建检查命令。
3. Windows、Linux 及受支持 Node 版本矩阵。
4. 文件失败注入、数据库迁移、重复导入、局部更新测试。
5. 打包后检查必需资源及版本，避免只验证源码而未验证产物。

测试失败或构建不一致时不得进入发布阶段。

### E02：统一运行时声明与实际依赖

位置：[Node 版本声明](<../package.json#L89-L90>)、[SQLite 导入](<../lib/redteam/store-core.js#L8>)、[内置事实库挂载](<../cordis.patch.yml#L67-L75>)。

包声明 Node ≥18，但内置数据层直接导入 `node:sqlite`，Node 18 不支持该模块。该问题属于兼容性声明不准确，不代表当前审查环境不能运行。

建议依据实际支持矩阵确定最低版本，并验证目标宿主的内置 Node 能力；若保留旧版基础功能，应按能力加载相关模块，给出清晰的不可用原因。

### E03：按职责逐步拆分大文件

审查基线中，[核心模块](<../lib/core.js>)约 8,380 行，[数据核心](<../lib/redteam/store-core.js>)约 5,385 行，后端入口与前端也承担多项职责。

建议按下列边界渐进拆分：

- 文件事务、唯一临时路径与恢复记录。
- 更新来源、资源清单、安装提交与版本状态。
- 数据写入、查询和迁移。
- 报告生成与业务筛选。
- 前端请求、状态及各页面组件。

每次只迁移一块职责，保留外部接口，先用回归测试固定行为。不以文件行数减少作为唯一验收目标。

### E04：建立数据量基准再做性能优化

当前已有批量预取等优化，不建议在没有测量的情况下全面改异步或加缓存。

优先测量：

- 不同资产量、服务历史量下的列表、详情和报告耗时。
- 多靶标列表读取是否逐库统计，数据库句柄数量是否持续增长。
- 同步数据库和文件操作对宿主事件循环的阻塞。
- 大页面的渲染行数、重复请求和过期响应覆盖。

基准需记录平台、运行时、数据规模、冷暖缓存和重复次数。优化时同时检查内存、数据正确性与界面响应，不只比较单次耗时。
